# Frontend (TypeScript, React, 3D, UI/UX)

> Принципы фронтенда, языка и визуального качества. Общие принципы — в [SKILL.md](../SKILL.md).

## Инструменты и стек

- **Язык: TypeScript** (и Node-тулинг, где уместно).
- **React + Vite** (или Next.js).
- **Клиентский state:** для небольших React/Vite PoC с локальным persistence по умолчанию используй Zustand. Доменное состояние, доступное нескольким частям приложения, и изменяющие его действия держи в store; компоненты вызывают эти действия напрямую, без цепочек доменных callback-пропов. Локальный `useState` оставляй для состояния конкретной формы, задания или визуального режима. Redux Toolkit нужен, когда состояние действительно требует нескольких доменных slices, сложного middleware или развитого event flow. Undo-историю храни отдельно от persisted state, если её восстановление после перезагрузки не требуется.
- **Dev server.** Если он есть в проекте, используй его во время frontend-работы и оставляй запущенным, чтобы владелец сразу видел изменения без ручной пересборки и перезапуска.
- **Маршрутизация разделов.** Отдельные пользовательские разделы приложения должны иметь собственные URL через штатный router стека (`react-router`, Next.js router и т.п.), чтобы Back/Forward, deep links и восстановление страницы работали нативно. Локальный state используй только для вкладок и режимов внутри одной страницы, а не для навигации между лендингом, кабинетом и редактором.
- **Структура простого React/Vite SPA без SSR.** Корень `src/` оставляй навигационным, а не складом реализации:
  - страницы размещай в `pages/<PageName>/`; page-specific компоненты, hooks, utils, styles и assets держи рядом со страницей в её вложенных каталогах;
  - компонент или hook поднимай в корневые `components/` или `hooks/` только когда он реально используется несколькими страницами;
  - каждый собственный UI-компонент размещай в отдельном каталоге `<ComponentName>/`, независимо от размера и наличия дочерних компонентов; точная структура и проверка описаны ниже;
  - stores размещай в `stores/`, общие helpers — в `utils/`, статические изображения и другие ресурсы — в `assets/`;
  - стили не держи в компонентах и не сваливай всё приложение в один CSS: глобальные reset/tokens — в `styles/`, остальные стили — рядом со страницей или компонентом;
  - для каждой страницы задавай `title` и нужные meta-теги через Helmet; provider подключай один раз в entrypoint;
  - в Vite и TypeScript настраивай alias `@/` на `src/` и используй его для межслойных импортов вместо глубоких `../../..`; соседние файлы внутри одного feature можно импортировать относительно;
  - `App` отвечает за providers и routing; доменная логика и разметка страниц в нём запрещены.
- **Browser automation.** Для проверки сайтов и локальных web-приложений используй MCP `playwright`: он сам запускает браузер. `browser:control-in-app-browser` используй только по явному запросу на Browser внутри Codex desktop; пустой `agent.browsers.list()` означает, что этот runtime недоступен. Если MCP `playwright` не загружен в текущую сессию, попроси перезапустить её, не подменяй Playwright встроенным Browser.
- **3D: Three.js / Babylon.js.**
- **Редактор конфигов в UI: MonacoEditor.**
- **UI-кит: gravity.** *(контекст конкретного проекта — не универсальный закон.)*
- **Lockfile принадлежит package manager.** После изменения зависимостей запускай штатную команду (`npm install`,
  `pnpm install`, `yarn install`) и принимай сгенерированный diff. Не редактируй и не читай lockfile вручную, если
  пользователь не попросил диагностировать конкретную проблему с dependency resolution.

## Структура компонентов — обязательное правило

- **Один компонент — один каталог.** Файл компонента: `components/<ComponentName>/<ComponentName>.tsx`. Правило одинаково для shared UI и компонентов страниц. Даже небольшой компонент из одного файла сразу получает свою папку. Файлы вида `components/EditorPanel.tsx` непосредственно в общем `components/` запрещены.
- **Внутренние компоненты принадлежат родителю.** Если компонент используется только внутри одного составного компонента, размещай его в `<Parent>/components/<Child>/<Child>.tsx`. Не складывай внутренние части разных компонентов в общий `pages/<Page>/components/`. Несколько самостоятельных именованных JSX-компонентов также не объединяй в один файл родителя.
- **Связанные файлы находятся рядом.** Стили, тесты, локальные типы и helpers размещай в каталоге владельца. Стили отдельного компонента не добавляй в общий CSS страницы; там остаются layout страницы и общие для неё правила. Создавай дополнительные файлы и подпапки только при наличии содержимого.
- **Поднимай только при реальном переиспользовании.** Общую часть нескольких компонентов размещай у их ближайшего общего владельца; shared UI — в общем UI-слое. Domain-neutral контролы с собственным API, например `Select`, следуют правилу shared UI выше, но тоже имеют собственную папку.
- **Импорты отражают владение.** Внутри компонента используй относительные импорты, между слоями — настроенный alias. Не создавай `index.ts` с единственным реэкспортом ради сокрытия структуры; существующий публичный API проекта сохраняй.
- **Проверяй до создания файла и перед сдачей.** Сначала определи владельца компонента и путь его каталога. Перед завершением просмотри дерево изменённого участка: в коллекциях `components/` должны находиться каталоги компонентов, а не россыпь `.tsx`, CSS и тестов. Проверь импорты, включая lazy imports и тесты. Успешный typecheck не заменяет эту проверку.
- **Существующая плоская структура не является исключением.** Не копируй её для новых компонентов. При изменении существующего компонента приведи его размещение к правилу вместе со связанными файлами и импортами; не реорганизуй заодно несвязанные части проекта.

Пример структуры (служебные файлы показаны только как пример размещения, создавать их заранее не нужно):

```text
src/
  components/
    Select/
      Select.tsx
      select.css
      Select.test.tsx
  pages/
    TourPage/
      TourPage.tsx
      tourPage.css
      components/
        InventoryPanel/
          InventoryPanel.tsx
          inventoryPanel.css
          InventoryPanel.test.tsx
          components/
            DeviceCard/
              DeviceCard.tsx
            Topology/
              Topology.tsx
```

## TypeScript

- **Типизация строго и явно.** Никаких `any` без причины. Вместо строковых литералов вразнобой — union-типы / `as const`, по аналогии с `Literal[...]` в Python.
- **Не дублировать валидацию фронт↔бэк.** Если бэк уже валидирует — не повторять на фронте. Источник истины один.
- **(Де)сериализация — явно.** Типы данных с бэка описывать явно, преобразования держать в одном месте, не размазывать.

## UI/UX — владелец придирчивый визуальный критик

Проверяй как он:

- **Выравнивание и отступы — по пикселю.** «Плохое выравнивание по вертикали», «проёбаны отступы, кнопки вплотную» — блокеры, не придирки.
- **Никаких лишних скроллов.** Контент помещается в окно; скролл — только где осмыслен. «3d-сцена не больше окна, скролл только где параметры».
- **Тёмная тема обязательна** — инпуты, 3D-сцены, все компоненты. Не опционально.
- **Прямая манипуляция.** Где уместно — интерактив на самом объекте/сцене, а не только в боковом UI. «Хочу тыкать и двигать прям на модели».
- **Базовые UI-контролы — общие.** Перед локальной реализацией ищи готовый контрол в design system и нативной платформе. Domain-neutral `Select`, `Dropdown`, `Tabs`, `Switch` и аналогичные контролы с собственными стилями или поведением сразу размещай в shared UI-слое с controlled API; feature-компонент передаёт только данные и обработчики. Предметную одноразовую композицию оставляй локальной.
- **Непрерывные hit-area.** В группе соседних однотипных кликабельных элементов путь курсора между ними не должен проходить через мёртвые зоны. Визуальные промежутки оформляй внутри общей интерактивной области или расширяй hit-area; hover и cursor должны оставаться непрерывными при переходе между элементами.
- **Согласованность с макетами и прошлым поведением** — источник истины. «Раньше был справа и корректно написан» → там и остаётся.
- **Состояния без гонок.** Не показывать «Choose Device» одновременно с лоадером; не фуллскрин-лоадер на модалку; loading/empty/error/hover/focus — все продуманы.
- **Закрываемые модалки закрываются по `Escape`.** Если содержимое живёт в `iframe`, обрабатывай `Escape` и в документе frame: событие не всплывает в родительский `<dialog>`.
- **Прогресс внятный.** Прогресс-бар на всю ширину, внутри — проценты и текущая команда.
- **Без магии в поведении.** Перпендикулярные стены не двигаются, параллельные нельзя переставлять — UI моделирует реальные ограничения.
- **Мобилка.** Фикс-хедеры, дерево, меню — проверь, что не разъезжается на узком экране.
- **Reference-driven.** Ориентируйся на качественные референсы (`bento3d.design` и т.п. — пример конкретного проекта), избегай generic-шаблонности.

## Анти-паттерны

- Generic AI-эстетика: шаблонные градиенты, безликие лейауты, кривые отступы, лишние скроллы.
- Фуллскрин-лоадеры, лишние ремаунты, UI-гонки состояний.
- `any` как способ заглушить типы.
- Дублирование констант/проверок/валидации между фронтом и бэком.
- Циклические зависимости между модулями.
